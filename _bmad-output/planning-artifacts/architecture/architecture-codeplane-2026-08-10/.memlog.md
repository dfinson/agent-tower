This is a distinct, existing per-repo analytics/settings surface, separate from DashboardScreen's single flat cross-repo KanbanBoard.
- (decision) [ADOPTED] RepoJobs.tsx is a historical/analytics job TABLE (fetchAnalyticsJobs, cost/tokens columns), not the live 3-column supervision Kanban (In Progress/Awaiting Input/Failed). It is a distinct concern from CAP-1 and is left untouched.
- (assumption) [ASSUMPTION] CAP-1 (repo-scoped board) is added as a new sibling route/tab under the existing /repos/:repoPath/* shell (e.g. /repos/:repoPath/board), reusing RepoLayout's sidebar and existing KanbanColumn/KanbanBoard rendering pieces, rather than adding a tab strip inside DashboardScreen. Rationale: RepoLayout already owns per-repo navigation chrome; duplicating a repo switcher inside DashboardScreen would create two competing repo-scoping UIs.
- (assumption) [ASSUMPTION] CAP-2/CAP-3 (projects overview + attention rollup) replaces RepoLayout's current silent auto-redirect-to-first-repo behavior at the bare /repos route: that index route renders the overview card grid instead of redirecting, and RepoLayout keeps redirecting only from deep-linked bare paths that resolve to nothing.
- (constraint) GET /settings/repos/{repo}/summary currently returns only activeJobCount, not a status breakdown (awaiting-input vs failed). CAP-2/CAP-3 need per-status counts, so this endpoint must gain awaiting_input_count and failed_count fields (additive, backward compatible) rather than the frontend re-deriving status from recentJobs (recentJobs is capped/paginated and not guaranteed to reflect true counts).
- (decision) [ADOPTED] Backend convention: route handlers stay thin and delegate to services/repositories (per project conventions); the new count fields are computed in the same job-count query path get_repo_summary already uses in settings.py, not a new endpoint.
- (decision) AD-1: Job status classification (in-progress/awaiting-input/failed) must be derived by ONE shared function reused by both DashboardScreen's KanbanBoard selectors (selectActiveJobs/selectSignoffJobs/selectAttentionJobs) and the new repo summary count logic, so a repo board and the overview badge can never disagree on what counts as 'awaiting input'. Binds: CAP-1, CAP-2, CAP-3. Prevents: frontend and backend classifying the same job into different buckets. Rule: classification logic lives in one place per layer (frontend: store/selectors.ts; backend: the query/service get_repo_summary already calls) and both are exercised by the same status-bucket enum/constants.
- (decision) AD-2: Repo-scoped board state (selected repo, via CAP-1) is carried entirely by the existing React Router :repoPath URL param under /repos/:repoPath/board -- no new query-string convention, no new client-only selection state. Binds: CAP-1. Prevents: two competing patterns (URL param vs query string) for the same kind of selection in the same app. Rule: any new repo-scoped route is a child of /repos/:repoPath, addressed via useParams, never a new top-level route with its own selection scheme.
- (decision) AD-3: The overview grid (CAP-2) and its rollup badge (CAP-3) are populated via a single batch call, not N sequential per-repo fetchRepoSummary calls. Binds: CAP-2, CAP-3. Prevents: an overview screen that fires one HTTP request per registered repo (N+1 on load, scales badly). Rule: add GET /settings/repos/summary (plural, batch) returning an array of the same per-repo shape used by the singular endpoint; the singular /summary/{repo} endpoint is kept for the existing RepoOverview detail page.
- (decision) AD-4: The overview grid and the repo-scoped board render from the same status-count shape end to end -- one TypeScript type (e.g. RepoBoardSummary extends the existing RepoSummaryResponse fields already in api/client.ts) generated from the OpenAPI schema, never a hand-duplicated interface. Binds: CAP-2, CAP-3. Prevents: card counts on the overview drifting out of sync with column counts on the board because of two independently hand-written shapes. Rule: reuse schema.d.ts-generated types via the existing friendly-alias layer in api/types.ts; do not hand-write a parallel summary type.

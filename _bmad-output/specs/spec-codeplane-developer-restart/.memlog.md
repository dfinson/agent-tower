topic: CodePlane developer restart through a detached helper
updated: 2026-08-07T16:55

- (direction) Express-mode spec distilled from the finalized CodePlane Developer Restart architecture and maintainer solution design.
- (capability) CAP-1 intent: A CodePlane developer can prepare a restart without taking down the current server; success: frontend build and backend compile/import preflight complete before any pause or stop, and any preparation failure leaves the current listener healthy.
- (capability) CAP-2 intent: A developer or managed CodePlane agent can hand restart execution to a process that survives the initiator and server; success: parent success occurs only after the detached helper claims the exact request and writes through the inherited log handle, and survival is proven on Windows and POSIX.
- (capability) CAP-3 intent: A restart applies the intended native CodePlane source while preserving the active runtime options; success: the helper launches the explicit target source using the recorded executable, host, port, dev/remote/provider/tunnel options, and refuses stale profiles or unresolved required secrets.
- (capability) CAP-4 intent: The helper can quiesce managed jobs and replace the current CodePlane process; success: it retrieves the complete running-job list before pausing, records individual pause failures, stops only the recorded old process, proves the port is unbound, and starts exactly one replacement.
- (capability) CAP-5 intent: A developer can distinguish a completed restart from mere port reachability; success: the replacement writes a request-specific readiness marker only after startup recovery and deferred remote validation, and the helper verifies that marker PID owns the configured port.
- (capability) CAP-6 intent: A remotely accessed development instance can return with its configured tunnel behavior; success: managed mode relaunches the recorded provider identity, external mode probes the exact hostname without process scans, and changed random origins are logged for manual reconnection.
- (capability) CAP-7 intent: A developer can diagnose restart progress and prevent concurrent helpers without product infrastructure; success: exact pending/claimed/started/ready files, one PID-plus-creation-time lock, bounded phase logs, stale-lock checks, and secret-free diagnostics behave deterministically.
- (constraint) Developer-only scope: add no REST route, MCP tool, frontend restart control, lifecycle database, gateway, supervisor, service manager, deployment generation, or automated rollback.
- (constraint) Native cross-platform scope: Windows instances use Windows-native paths/processes and POSIX instances use POSIX-native paths/processes; no cross-environment path translation or launch adapter.
- (constraint) Existing recovery remains authoritative: the helper never sends resume calls, and documented plan-mode waiting_for_approval failure behavior is accepted.
- (constraint) Fail closed before outage: stale launch profiles, invalid target source, unreplayable required secrets, build/preflight failure, spawn failure, adoption timeout, lock conflict, or running-job-list failure must leave the current server running.
- (constraint) After the first pause request, the helper must continue toward restart while recording per-job pause failures, avoiding a partially paused server left serving indefinitely.
- (constraint) Use existing project tooling and dependencies; Python interactions run through uv, while the detached child uses the recorded active Python executable without dependency synchronization.
- (constraint) Default bounds: adoption 5 seconds, response grace 2 seconds, pause wait 10 seconds, stop 15 seconds, readiness 60 seconds, and remote probe 30 seconds; all are explicit CLI overrides and logged.
- (constraint) Backend preflight runs compileall over backend and tools plus import of backend.app_factory from the target source using the recorded active executable, without dependency installation or runtime mutation.
- (constraint) Successful requests and markers are removed after terminal logging; failed claimed requests and markers are retained for diagnosis until the next explicit cleanup; the restart log rotates at 5 MiB with one backup.
- (assumption) Manual local recovery after post-stop failure is acceptable because this command is only for CodePlane developers.
- (assumption) Temporary browser, SSE, WebSocket, and MCP disconnects are acceptable and remote users reconnect manually.
